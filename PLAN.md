# Plan: Deep Memory Curation (`neurox curate`)

## Goal

Add a curation system that uses a large external model (Gemini 2.5 Flash) to periodically review entire namespaces, delete noise, recalibrate importance weights, and generate quality reflections. The current small local model (Ollama) keeps doing real-time gate/promotion work. The large model acts as a supervisor that corrects the small model's mistakes.

This also migrates automatic reflections from the small model to the curator provider, so all synthesized insights are high quality.

## Business Context

- **Users**: Any neurox user whose memory has accumulated noise over time
- **Problem**: Current memory is ~60% junk (step logs, micro-details at importance 0.01, duplicate reflections). The local LLM (Ollama) isn't smart enough to filter or rank properly. Reflections generated by the small model are generic and duplicated.
- **Expected outcome**: After running `neurox curate`, a namespace goes from hundreds of noisy observations to a clean, well-weighted memory where recall actually surfaces the right things first.
- **Cost**: ~$0.05 per full curation with Gemini 2.5 Flash (86K tokens input for 796 observations). Negligible.
- **User priorities**: A YAML file where the user declares what topics matter to them. The curator uses these to protect and boost relevant observations.
- **Curation decisions dataset**: Every curation run saves its decisions (DELETE/KEEP + reason) for potential future fine-tuning.

## Technical Context

### Current architecture
- **LLM Provider interface**: `llm.Provider` with `Complete(ctx, prompt) (string, error)` — implementations: `OllamaProvider`, `RemoteProvider`, `Disabled`
- **Config**: `config.Config.LLM` has `Provider`, `OllamaURL`, `OllamaModel`, `RemoteURL`, `RemoteAPIKey`, `RemoteModel`
- **Consolidation pipeline**: `internal/consolidate/pipeline.go` runs every 30 min — decay, promote, dedup, contradictions, reflections, evict, GC
- **Reflect engine**: `internal/reflect/engine.go` — threshold of 20 new observations triggers reflection via LLM. Currently uses the same Ollama provider as everything else.
- **MCP server**: `internal/mcp/` — tools registered in `server.go`, handlers in `handlers.go`, tool definitions in `tools.go`
- **CLI dispatch**: `main.go` switch on `os.Args[1]`, `flag.NewFlagSet` per subcommand
- **DB schema**: `internal/db/schema.sql` + numbered migrations. Current version: 5.
- **Default Ollama model**: `qwen2.5:3b` (hardcoded in `internal/llm/ollama.go`)

### Key findings from data analysis
- 796 total observations, 345K characters (~86K tokens)
- 487 observations with importance < 0.1 (61%)
- 26 duplicate reflections (all generic, from Ollama)
- 37 clearly junk entries (step logs, "Successful Build", "Branch Cleanliness")
- 83 clearly valuable entries (importance ≥ 0.7 or access_count ≥ 3)
- 11 namespaces, largest: email-template-tool (399 obs)

### Gemini 2.5 Flash API
- Endpoint: OpenAI-compatible (`/chat/completions`) via `https://generativelanguage.googleapis.com/v1beta/openai`
- Pricing: $0.30/1M input, $2.50/1M output (under 200K context)
- Context window: 1M tokens — entire memory fits easily per namespace
- Auth: API key via `Authorization: Bearer` header
- The existing `RemoteProvider` in `internal/llm/remote.go` already supports OpenAI-compatible endpoints — Gemini works with it directly

### Ollama model upgrade
- Current default: `qwen2.5:3b`
- New recommended: `qwen3:8b` (user preference)
- This is config-only — change `defaultOllamaModel` constant

### Step 3: Core curation engine
- **What**: Create `internal/curate/engine.go` — the heart of the feature:
  1. `Engine` struct holding `db`, `curator llm.Provider`, `priorities Priorities`
  2. `CurateNamespace(ctx, namespace string, dryRun bool) (NamespaceReport, error)`:
     - Load ALL observations for the namespace from DB (id, title, content, observation_type, importance, access_count, layer, tags, retention, staleness)
     - Load priorities for this namespace
     - Build the curation prompt (see prompt design below)
     - Call curator LLM with the full namespace content
     - Parse structured JSON response — array of decisions: `{id, action, new_importance, reason}`
     - If not dry-run: execute actions on DB (soft-delete for DELETE, update importance for KEEP)
     - Return `NamespaceReport` with stats
  3. `CurateAll(ctx, dryRun bool) (FullReport, error)`:
     - Get all active namespaces
     - Call `CurateNamespace` for each
     - Aggregate into `FullReport`
  4. Decision types:
     ```go
     type Decision struct {
         ID            string  `json:"id"`
         Action        string  `json:"action"`        // "DELETE" or "KEEP"
         NewImportance float64 `json:"new_importance"` // 0.0-1.0, only for KEEP
         Reason        string  `json:"reason"`
     }
     ```
  5. Report types:
     ```go
     type NamespaceReport struct {
         Namespace       string
         Before          int      // total obs before
         Deleted         int
         Recalibrated    int
         Protected       int      // matched user priorities
         TopTopics       []string // main topics detected
         Decisions       []Decision // full log for dataset
     }
     ```

  **Prompt design** — single prompt per namespace:
  ```
  You are a memory curator for an AI coding agent. Review ALL observations below
  and decide for each one: DELETE (noise/junk/duplicate) or KEEP (with recalibrated importance 0.0-1.0).

  USER PRIORITIES (protect and boost observations matching these):
  {priorities}

  RULES:
  - DELETE: step logs, plan status, "successful build", micro-implementation details,
    near-duplicates (keep the better one), empty/vague content, temporary state
  - KEEP with HIGH importance (0.7-1.0): architectural decisions, user preferences,
    recurring patterns, reusable gotchas, cross-project insights
  - KEEP with MEDIUM importance (0.4-0.7): useful technical details, specific bugfixes
    with root cause, configuration that's hard to rediscover
  - KEEP with LOW importance (0.1-0.3): minor details that might be useful someday
  - Observations matching user priorities should get importance >= 0.7
  - Between near-duplicates, keep the one with better content and DELETE the other

  OBSERVATIONS ({count} total):
  {observations as numbered JSON array}

  Respond with a JSON array. One entry per observation, no exceptions:
  [{"id": "...", "action": "DELETE"|"KEEP", "new_importance": 0.0-1.0, "reason": "brief reason"}]
  ```

- **Why**: This is the core value — a large model with full namespace context making intelligent cleanup and recalibration decisions.
- **Where**: `internal/curate/engine.go`, `internal/curate/prompt.go` (prompt building)
- **Acceptance**:
  - Loads all observations for a namespace
  - Builds prompt with priorities included
  - Parses JSON response from LLM correctly
  - Executes DELETE (soft-delete) and KEEP (update importance) actions on DB
  - Dry-run mode makes no DB changes
  - Returns detailed NamespaceReport
  - Handles LLM errors gracefully (abort namespace, report error, continue to next)
- **Status**: [x] done

### Step 4: Curation decisions log (migration + store)
- **What**:
  1. Create migration `006_curation.sql`:
     ```sql
     CREATE TABLE curation_runs (
         id TEXT PRIMARY KEY,
         namespace TEXT NOT NULL,
         status TEXT NOT NULL DEFAULT 'running'
             CHECK (status IN ('running', 'completed', 'failed')),
         observations_before INTEGER DEFAULT 0,
         observations_deleted INTEGER DEFAULT 0,
         observations_recalibrated INTEGER DEFAULT 0,
         observations_protected INTEGER DEFAULT 0,
         dry_run INTEGER NOT NULL DEFAULT 0,
         curator_model TEXT,
         started_at TEXT NOT NULL DEFAULT (datetime('now')),
         completed_at TEXT,
         error_message TEXT
     );

     CREATE TABLE curation_decisions (
         id TEXT PRIMARY KEY,
         run_id TEXT NOT NULL REFERENCES curation_runs(id) ON DELETE CASCADE,
         observation_id TEXT NOT NULL,
         action TEXT NOT NULL CHECK (action IN ('DELETE', 'KEEP')),
         old_importance REAL,
         new_importance REAL,
         reason TEXT,
         created_at TEXT NOT NULL DEFAULT (datetime('now'))
     );

     CREATE INDEX idx_curation_decisions_run ON curation_decisions(run_id);
     CREATE INDEX idx_curation_runs_namespace ON curation_runs(namespace);
     ```
  2. Register migration in `internal/db/db.go` (version 6)
  3. Embed the SQL file
  4. Save decisions after each curation run in `internal/curate/engine.go`
- **Why**: Decisions log serves two purposes: audit trail (what did the curator do?) and future fine-tuning dataset.
- **Where**: `internal/db/006_curation.sql`, `internal/db/db.go`
- **Acceptance**:
  - Migration applies cleanly on existing databases
  - `curation_runs` and `curation_decisions` tables created

## Risks / Notes

- **LLM response parsing**: The curator prompt asks for a JSON array. Large models are generally reliable at this, but we need robust parsing with fallback — if the response isn't valid JSON, abort that namespace and report the error, don't crash.
- **Large namespaces**: `email-template-tool` has 399 observations (~170K chars, ~43K tokens). This fits within Gemini Flash's 1M context window, but approaches the 200K token tier where pricing doubles. For namespaces >200K tokens, consider splitting into batches of 200 observations. For now, all our namespaces fit comfortably.
- **Atomic curation**: All DELETE and KEEP actions for a namespace should run in a single DB transaction. If any action fails, rollback the entire namespace curation.
- **Backward compatibility**: If `curator` config is not set, everything works as before. The `curate` command prints a helpful message explaining how to configure it. Reflections fall back to Ollama.
- **Gemini API compatibility**: Gemini's OpenAI-compatible endpoint works with the existing `RemoteProvider`. The URL is `https://generativelanguage.googleapis.com/v1beta/openai`. Auth is `Bearer {API_KEY}`. No new HTTP client code needed.
- **Default Ollama model change**: Changing from `qwen2.5:3b` to `qwen3:8b` means users need to have `qwen3:8b` pulled in Ollama. If it's not available, Ollama will return an error and the system degrades to `Disabled` — existing behavior. Document this in the config.
- **Priorities file optional**: If `priorities.yaml` doesn't exist, curation still works — it just doesn't have user guidance for what to protect/boost. The curator uses its own judgment.
- **Curation decisions as training data**: The `curation_decisions` table stores every decision with reason. This is the dataset for potential future fine-tuning of a specialized curation model. No action needed now — just accumulate data.
- **Existing PLAN.md**: The previous plan (neurox update command) had Steps 1-2 done, Steps 3-5 pending. That work is preserved in git history. This plan replaces it entirely.
